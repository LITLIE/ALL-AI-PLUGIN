# AgentWorkbench 项目成熟度评估

> 评估日期：2026-09-02 · 评估人：大湾区靓仔（项目总监）
> 评估方式：全量源码通读 + 真实运行验证（CLI / HTTP / SSE / 安全边界 / 测试套件），非文档自述采信
> 目标基线：参照 openai/codex-plugin-cc 插件式接入思路，本地运行的「AI Agent 统一编排工作台」，聚合 Trae / WorkBuddy / Codex / Claude，主控 Agent 负责拆解、分派、跟踪、验收

---

## 0. 一句话结论

**骨架极扎实，血肉基本没长。**

事件总线、验收闸门、审计回放这三条「信任底座」做得相当过硬（这是我见过同规模项目里少有的严谨度），但项目最核心的承诺——**把真实 AI Agent 聚合进来并跑起来**——目前是 **0/3**：Claude、Codex、Trae 三个真实后端全部无法执行，唯一能跑的是内置的 Echo 假适配器。

更值得警惕的是：**36/36 测试全绿，却一条真实 Agent 都没覆盖到。** 测试套件当前提供的是"假信心"——它能证明 Echo 链路无误，但对 Claude/Codex/Windows spawn 的三处致命缺陷完全失明。

综合判定：**P0 功能完成度约 40%，距最终愿景约 30%。**

### 复评进展（M1/M2 实施后）

本评估形成后，已完成 M1 真实执行底座、M2 Codex app-server 生命周期和 M3 配置契约：Windows shim 解析、配置透传、Claude/Codex fixture 契约测试、Codex JSON-RPC session/turn、嵌套完成通知、`event_msg/task_complete`、服务器错误、进程提前退出、超时和 AbortController 中断，以及风险/能力/schema 校验均已接通。当前 `workbench` 全量测试为 **58/58 pass**，但这不等同于真实模型调用验证：本机 `codex` 探测成功，`claude` 仍因 Node 进程 PATH 不可见而不可用；未执行真实 Codex 任务以避免未经确认的额度消耗和工作区影响。

因此，原文中的 P0-1、P0-2、P0-3、P0-4、P0-6 已解决或显著收敛；P0-5（human-bridge）仍未实现。随后 M3 配置规范化也已完成：风险等级、能力标签、adapter 类型别名和注释安全解析均有统一 schema 与测试覆盖。后续优先级应转向 M4 的隔离、快照、diff、apply/rollback，再进入 Planner/DAG，而不是重复处理 Codex 基础生命周期。

## 3. P0 缺陷清单（阻断项，必须优先修）

### P0-1 · Windows spawn 解析错误 —— 真实 Agent 全部探测失败

- **位置**：`core/utils.mjs` `findInPath()` (L69-91) + `spawnPlan()` (L17-64)
- **根因**：`findInPath('claude')` 遍历 PATH 目录，命中 `C:\Users\wzc\AppData\Roaming\npm\claude`（**无扩展名的 bash shim**，npm  installs 时同时生成 `claude` / `claude.cmd` / `claude.ps1`），立即返回。回到 `spawnPlan`，判断 `resolved.endsWith('.cmd')` → **false**，于是走 `{command:'claude', shell:false}` 分支 → Node 在 Windows 上无法 spawn 无扩展名脚本 → **ENOENT**。
- **证据**：见 §1.3
- **严重性**：致命。这是"聚合真实 Agent"的第一道门，门是坏的。
- **额外问题**：这**直接违反 ADR-002**。ADR-002 白纸黑字写「统一入口复用 `spawnPlan()` 语义（移植自 `plugins/agent-crew/server/lib/dispatch.mjs`）……**行为不变**」，但实现时**重写了一份且写错了**。
- **修法**（半天）：**直接搬** `plugins/agent-crew/server/lib/dispatch.mjs` 的 `resolveExecutable()` + `spawnPlan()`。那份实现是对的——它按 PATHEXT 顺序探测 `.COM/.EXE/.BAT/.CMD`，优先命中 `.cmd`，再经 `cmd.exe /d /s /c` 路由。
- **验收**：`node awb.mjs agents:probe` 输出 `claude-stream: {"ok":true,"version":"2.1.258"}`

### P0-2 · Claude 适配器结构上无法产出终态事件

- **位置**：`adapters/claude-stream-json.mjs` `run()` (L32-110)
- **根因（三重）**：
  1. `run()` 只 `yield` 了两次 `run.started`（L34、L91 **重复**），然后 `await` 进程关闭——**从不 yield 任何终态事件**。
  2. 真正的事件全部走 `onEvent?.(ev)` 回调发出。但 `Orchestrator._executeRun` 调用的是
     `adapter.run({ taskId, runId, prompt, cwd, timeoutMs, signal })` —— **根本没传 `onEvent`**，回调是 `undefined`，事件全部蒸发。
  3. 硬编码 `spawn('claude', [...])`，完全无视 `agents/claude-stream.json` 里的 `command`/`args`/`env`。
- **后果**：即使解除 Echo 限制，Claude 也 **100% 失败**——流结束无终态事件 → `_failRun("Adapter stream ended without terminal event")`。
- **修法**：改用异步队列（`AsyncQueue`）把 stdout 回调里的事件 push 进队列，generator 从队列 `yield`；删除重复 `run.started`；args 从 config 读。
- **验收**：`task:dispatch --agent claude-stream` 真实返回 `run.completed` 且 `cost > 0`

### P0-3 · Codex 适配器轮询循环永不检测完成

- **位置**：`adapters/codex-app-server.mjs` L102-113
- **根因**：
  ```js
  while (Date.now() - startPoll < timeoutMs) {
    await new Promise(r => setTimeout(r, 300));
    const elapsed = Date.now() - startTs;
    if (elapsed > timeoutMs) { yield run.timeout; ... proc.kill(); return; }
  }
  ```
  循环体**只判超时，从不检查 turn 是否完成**。`connect()` 里辛苦收集的 `notifications` 数组在 `run()` 中**从未被读取**。
- **后果**：每一次 Codex 运行都会**耗尽超时后按 timeout 终止**，无论任务多简单。
- **修法**：轮询 `notifications`，检测 `turn/completed` / item 完成通知；先发 `turn/interrupt` 留 3s 宽限，再 `taskkill /T /F` 杀进程树（ADR-002 已定方案，未落地）。
- **验收**：Codex 简单任务在超时前返回 `run.completed`

### P0-4 · 适配器契约未传递 config —— "配置驱动"名不副实

- **位置**：`core/orchestrator.mjs` L189-196
- **根因**：`adapter.run()` 只收到 6 个参数，**不含 `agentConfig`**。
- **后果**：`agents/*.json` 里的 `command`、`args`（含 `{{prompt}}` 模板）、`env`、`healthCheck`、`timeoutDefault`、`maxRetries`、`riskLevel`、`sessionMode` **全部是死配置**，写了也不生效。
- **违反**：AC-01「新增适配器配置（不改核心代码）即可生效」未达成——现在每接一个 Agent 都要写新 JS。
- **修法**：`adapter.run({ taskId, runId, prompt, cwd, timeoutMs, signal, agentConfig, onEvent })`，并让适配器统一从 `agentConfig` 取命令与参数模板。

### P0-5 · human-bridge 端到端不通，且探活造假

- **位置**：`adapters/human-bridge.mjs` `run()` (L58-68)
- **根因**：yield 出 `run.started` → `run.awaiting-human` → `run.briefing-ready` → `run.awaiting-human`，**无终态事件** → 立即被判失败。
- **连带**：`/api/bridges/:id/submit` 返回 **501**；`processReceipt()` 函数写了但无调用方；UI 无粘贴回填界面。
- **更糟**：`probe()` 永远返回 `{ok:true}`，导致 `trae-solo-bridge` 在 `agents:list` 里显示 **available**——**假阳性**，用户会以为能用。
- **修法**：引入 `awaiting-human` 合法挂起态（不算失败）+ 实现 submit 端点 + UI 粘贴面板 + probe 改为真实校验。

### P0-6 · 测试套件零真实适配器覆盖（假信心）

- **证据**：`grep -rl "claude\|codex" test/` → **零命中**。1025 行测试、36 个用例，全部只跑 Echo。
- **后果**：上面 P0-1/2/3 三个致命缺陷，测试一条都没抓到。
- **修法**：新增 `test/adapter-contract.test.mjs`，用**假 CLI 脚本**（写一个 `.cmd` + 无扩展名 shim 的 fixture 到临时目录）驱动契约测试，不需要真 token、不联网、秒级完成。每个适配器都必须通过同一份契约：
  `run.started` → 至少一个非终态事件 → 恰好一个终态事件 → 流正常关闭。

## 7. 改进路线图

> 原则：**先打通一条真实链路，再铺功能面。** 现在最大的风险不是功能少，而是"看起来很多、实际跑不通"。

### M1 · 打通真实 Agent 执行（P0，约 1 天）★最高优先

| 任务 | 动作 | 验收标准 |
|---|---|---|
| M1.1 | 用 agent-crew 的 `resolveExecutable`+`spawnPlan` **整体替换** `core/utils.mjs` 同名实现（落实 ADR-002「禁止重写」） | `agents:probe` 显示 claude `2.1.258`、codex `0.150.1` 均 `ok:true` |
| M1.2 | 修适配器契约：`adapter.run()` 增加 `agentConfig` + `onEvent` 两个入参 | 适配器可从 config 读取 command/args/env |
| M1.3 | 重写 `claude-stream-json.mjs`：异步队列驱动事件、删除重复 `run.started`、超时走 killProcessTree | `task:dispatch --agent claude-stream` 真实完成且 `cost>0` |

## 8. 给项目总监的三条硬建议

1. **测试策略必须改。** 36/36 全绿却漏掉三个致命缺陷，说明测试测错了地方。立即加"适配器契约测试"——用假 CLI fixture 驱动，不耗 token、不联网，让每个新适配器过同一份考卷。**没有契约测试的适配器层，等于没有适配器层。**

2. **别再重写已有实现。** P0-1 的根因就是 ADR-002 明令"复用 spawnPlan、禁止重写"，结果重写了一份错的。agent-crew 里那份是**本机实测验证过**的。搬过来，加测试，完事。**在零依赖约束下，复制粘贴 + 测试 比重写更工程化。**

3. **M1 不完成，不要动 M4 之后的任何功能。** 现在堆 diff、worktree、审批，都是在一个跑不通 Agent 的底座上盖楼。先把 Claude 真实跑通一次，你会立刻发现一批文档里没写的问题——那时候再决定优先级，比现在拍脑袋准得多。
